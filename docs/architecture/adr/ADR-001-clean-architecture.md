# ADR-001: Clean Architecture の採用

**ステータス**: Accepted  
**作成日**: 2026-10-07  
**決定者**: プロジェクト推進者  
**関連要求**: BR-01（技術スタック方針）

---

## 1. コンテキスト

Project Dama は MVP を Next.js（Web）で構築しつつ、将来的に Flutter（モバイル）へ移行する計画を持つ。フレームワーク移行時にビジネスロジックの再実装コストが発生することを防ぎ、長期的な保守性を確保する設計方針が必要である。

また、4つの機能領域（食事・光・運動・デジタルデトックス）は独立したドメインとして扱われるべきであり、各領域の変更が他領域に影響を与えないよう境界を明確にする必要がある。

---

## 2. 決定

**Clean Architecture** を採用し、以下の層構造で実装する。

```
src/
├── domain/          # 純粋ドメインモデル・ビジネスルール（外部依存禁止）
├── usecases/        # アプリケーションユースケース・オーケストレーション
├── adapters/        # インターフェース定義（Repository Protocol / Interface）
├── routes/          # HTTP リクエスト・レスポンス境界（Next.js API Routes / Pages）
└── infrastructure/  # Supabase・外部API等の具体実装
```

**依存方向ルール**:
```
routes → usecases → domain
adapters → usecases → domain
infrastructure → adapters
```

---

## 3. 理由

| 理由 | 詳細 |
|---|---|
| **フレームワーク独立性** | `domain/` と `usecases/` は Next.js / Flutter いずれにも非依存であるため、フロントエンド移行時も再利用可能 |
| **テスト容易性** | ドメイン層・ユースケース層は外部依存がなく、純粋な単体テストが書ける |
| **変更容易性** | Supabase を別DBに差し替える場合も `infrastructure/` のみ変更すれば済む |
| **チーム独立性** | 4機能領域を別サブディレクトリで管理することで、並行開発の競合を最小化できる |

---

## 4. トレードオフ

| メリット | デメリット |
|---|---|
| 長期保守性が高い | 初期のボイラープレートが増える |
| テストが書きやすい | 小規模 MVP には過剰に感じる場合がある |
| フレームワーク移行コストが低い | チームへのアーキテクチャ学習コストが発生する |

---

## 5. 却下した選択肢

- **Next.js のみのシンプル構成（ページ + APIルートに全ロジック）**: フレームワーク依存が強く、Flutter 移行時にロジックを全書き直しになる。
- **モノリシックなバックエンド（Node.js / Python 独立サーバー）**: MVP でのインフラ管理コストが不必要に増大する。
